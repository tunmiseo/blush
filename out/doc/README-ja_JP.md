`ble.sh`<sup><a href="#discl-pronun">†1</a></sup> (*Bash Line Editor*)
is pure Bash<sup><a href="#discl-pure">†2</a></sup>
A scripted command line editor that replaces the standard GNU Readline.

The current development version is 0.4.
This script can be used with Bash 3.0 or later, but from the viewpoint of speed and functionality, we recommend using it with Bash 4.0 or later releases.
It is also assumed that basic POSIX commands exist.
Currently, only `UTF-8` is supported as the character code.
This script is provided under the [**BSD License**](LICENSE.md) (3-clause BSD License).


## The way it came, the way it came, the end

This project started as a small experiment in a corner of `.bashrc`.
I was inspired by an article on `zsh-syntax-highlighting` in May 2013.
At first, I started this experiment thinking that syntax coloring could be easily achieved by writing a few hundred lines of code.
I realized that this would not be possible unless I immediately rewrote the line editor from the ground up.
I gave it the name `ble.sh` after moving the code into a separate file.
This name mimics Zsh's line editor (*ZLE* (*Zsh Line Editor*)).
However, I remember that I changed the extension to `.sh` keeping in mind that it was written in a shell.
I am often asked how to read `ble.sh`, but as I wrote at the beginning, there is no particular way to read it.
The first experiment ended with me fiddling with the code for about two weeks and concluded that it was possible to create a line editor in principle.
Full-scale implementation began in February 2015, and it was released in December.
At that point, it was complete enough to be used as a line editor for everyday use.
Implementation of Vim mode began in September 2017 and was first completed in March 2018.
Subsequently, the expansion of completion began in August 2018 and was completed in February 2019.
I'm currently in the middle of maintenance, so I don't know when it will be completed, but I'm vaguely thinking about adding the following features.

## Limitations and assumptions

There are limitations due to the implementation of `ble.sh`.
Problems can occur due to user settings or interference with other Bash frameworks.

- By default, `ble.sh` does not set the `PIPESTATUS` after the previous command line execution due to execution costs. You can reference `BLE_PIPESTATUS` instead.
  If you really need to use these values ​​via `PIPESTATUS`, use the setting `bleopt exec_restore_pipestatus=1`.
- By default, `ble.sh` assumes that `PROMPT_COMMAND` and `PRECMD` hooks do not change the cursor position and layout within the terminal, for smoother drawing.
  If you have settings for `PROMPT_COMMAND` and `PRECMD` to produce output or change cursor position, use the setting `bleopt prompt_command_changes_layout=1`.
- `ble.sh` assumes that shell variables and environment variables with common variable names (such as `LC_*`) are not global and read-only variables.
  In Bash, the read-only attribute of global variables also imposes restrictions on the local scope of functions.
  That is, you cannot even define different local variables with the same name.
  This problem is not a limitation specific to `ble.sh`; all Bash frameworks are affected by global read-only variables.
  Setting read variables in the global scope is generally considered deprecated unless there are security reasons (see [[1]](https://lists.gnu.org/archive/html/bug-bash/2019-03/threads.html#00150), [[2]](https://lists.gnu.org/archive/html/bug-bash/2020-04/threads.html#00200), [[3]](https://mywiki.wooledge.org/BashProgramming?highlight=%28%22readonly%22%20flag,%20or%20an%20%22integer%22%20fla g,%20but%20these%20are%20mostly%20useless,%20and%20serious%20scripts%20shouldn%27t%20be%20using%20them%29#Variables)).
  `ble.sh` also replaces the built-in command `readonly` with a shell function that blocks making global variables read-only.
  As an exception, it is possible to make all uppercase variables (except those used internally by `ble.sh`) and variables of the form `_*` (except `_ble_*` and `__ble_*`) read-only.
- `ble.sh` overrides Bash's built-in commands (`trap`, `readonly`, `bind`, `history`, `read`, `exit`) with shell functions and adjusts their behavior so that they do not interfere with `ble.sh`.
  Correct behavior cannot be guaranteed if the user or another framework calls the original built-in directly, or overwrites the shell functions defined in `ble.sh` with another shell function.
- Shell and terminal settings are different for line editor and command execution. `ble.sh`
  makes the necessary adjustments for the line editor and configures the settings for executing the command specified by the user.
  Restore as much as possible. However, for various reasons, some settings may be intentionally changed.
  It may not be restored or it may not be possible to restore it. For more information
  [wiki](https://github.com/akinomyoga/ble.sh/wiki/Internals#internal-and-external)
  (English) has information.

## criticism

- <sup><a id="discl-pronun" href="#discl-pronun">†1</a></sup>Q. "I don't know how to read ble.sh"---
  A. You can read `ble.sh` as you like, but the shortest version should be /blɛʃ/.
  However, personally, I read it in my head as /biːɛliː/ or /biːɛliː dɑt ɛseɪtʃ/.
  We hope that you will take the reading of the headings as a reference only.
- <sup><a id="discl-pure" href="#discl-pure">†2</a></sup>Q. "It can't be pure Bash because it executes a command.
  What is Pure Bash?"---
  A. It means that the line editor itself is written in pure Bash.
  Of course, if the user enters and executes an external command, that external command will be called.
  Additionally, `stty` (POSIX) is called to properly configure the TTY before and after executing a user command.
  In addition, in order to speed up processing, initialization / termination processing,
  It uses POSIX standard commands when processing large amounts of data (completion, pasting, etc.).
  The original goal of implementing `ble.sh` was not to implement it in pure Bash;
  The goal is to achieve high-speed operation while maintaining Bash compatibility in a POSIX environment.
  Although pure Bash can reduce the cost of `fork` &amp; `exec` in most cases,
  If implementation via external commands is more efficient in your particular case,
  `ble.sh` favors implementation with external commands over pure Bash implementation.

# 1 How to use

## 1.1 How to build from source <sup><a id="get-from-source" href="#get-from-source">†</a></sup>

### ble.sh generation

To generate `ble.sh` you need `gawk` (GNU awk) and `gmake` (GNU make).
It can be generated with the following command.
If GNU make is installed as `gmake`, use `gmake` instead of `make`.
```console
$ git clone --recursive https://github.com/akinomyoga/ble.sh.git
$ cd ble.sh
$ make
```
A script file `ble.sh` is generated in the subdirectory `ble.sh/out`.

### trial

You can try the generated `ble.sh` using the `source` command.

```console
$ source out/ble.sh
```

### Install<sup><a id="package" href="#install">†</a></sup>

Use the `make install` command to install into a specified directory.

```bash
# Installed to ~/.local/share/blesh
make install

# Install in specified directory
make install INSDIR=/path/to/blesh
```

The installation directory for the main file `ble.sh` and related script files can be specified using the Make variable `INSDIR`.
You can specify where the license and documentation will be installed using the Make variables `INSDIR_LICENSE` and `INSDIR_DOC`.
When `INSDIR` is specified, `INSDIR_LICENSE` and `INSDIR_DOC` default to `$INSDIR/licenses` and `$INSDIR/doc`, respectively.
When `INSDIR` and `DESTDIR`/`PREFIX` described below are not specified, the default values ​​of `INSDIR`, `INSDIR_LICENSE`, and `INSDIR_DOC` are
These are `$data/blesh`, `$data/blesh/licenses`, and `$data/doc/blesh`, respectively.
However, `data` refers to `${XDG_DATA_HOME:-$HOME/.local/share}`.

When the make variable `USE_DOC=no` is specified, processing of documentation files is disabled.

By default, comment lines and blank lines in the code are automatically removed during installation.
If you want to keep comments and blank lines, specify `strip_comment=no` as an argument to `make`.

For setting up `.bashrc`, see [Section 1.3] (#set-up-bashrc).

### Package creation<sup><a id="package" href="#package">†</a></sup>

Package authors use the Make variables `DESTDIR` and `PREFIX` to set `INSDIR`,
Default values ​​for `INSDIR_LICENSE` and `INSDIR_DOC` can be set at once.

```
# Package creation - example 1
make install DESTDIR=/tmp/blesh-package PREFIX=/usr/local

# Package creation - example 2
make install DESTDIR="$build" PREFIX="$prefix" \
  INSDIR_LICENSE="$build/$prefix/share/licenses/blesh"

# Package creation - example 3
make install DESTDIR="$build" PREFIX="$prefix" \
  INSDIR_LICENSE="$build/$prefix/share/blesh/doc" \
  INSDIR_DOC="$build/$prefix/share/blesh/doc"

# Package creation - Example 4
make install USE_DOC=no DESTDIR="$build" PREFIX="$prefix"
```

When the Make variable `DESTDIR` or `PREFIX` is specified instead of `INSDIR`,
The value of `INSDIR` is set to `$DESTDIR/$PREFIX/share/blesh`,
The default location of license and documentation files `INSDIR_LICENSE` and `INSDIR_DOC` is `$DESTDIR/$PREFIX/share/doc/blesh`.

#### `_package.bash`

By placing the script file `_package.bash` in `${prefix}/share/blesh/lib/_package.bash`,
You can specify the package update method used by `ble-update`.
The script file `_package.bash` defines the variables and functions shown below.
However, replace `XXX` with the name of your package management system.

```bash
# ${prefix}/share/blesh/lib/_package.bash

_ble_base_package_type=XXX

function ble/base/package:XXX/update {
  update-the-package-in-a-proper-way
  return 0
}
```

An exit status of 0 for the shell function indicates that the update was successful, and `ble.sh` will be automatically reloaded after the update process is complete.
If the shell function exits with status 6, the timestamp of `ble.sh` is checked after the update process is completed, and reloading occurs only if `ble.sh` is newer than the start time of the current session.
If the shell function exits with status 125, the update process built into `ble.sh` is attempted.
Otherwise, the update process will be interrupted. In this case, make sure your shell function prints a message explaining the situation.
As a specific example, please refer to [`_package.bash`](https://aur.archlinux.org/cgit/aur.git/tree/blesh-update.sh?h=blesh-git) of the `AUR` package.

## 1.3 Setting `.bashrc`<sup><a id="set-up-bashrc" href="#set-up-bashrc">†</a></sup>

If you use it regularly in an interactive shell, set it in `.bashrc`.
Simply `sourcing` `ble.sh` will work in most cases, but
To make it work more reliably, write the code as follows.
```bash
# bashrc

# Add the following near the top of .bashrc.
[[ $- == *i* ]] && source -- /path/to/blesh/ble.sh --attach=none

# In between, I will describe the contents of a normal bashrc.

# Add the following near the end of .bashrc.
[[ ! ${BLE_VERSION-} ]] || ble-attach
```

When calling `source -- /path/to/ble.sh` and `ble-attach`,
Make sure that the standard streams (`stdin`, `stdout`, `stderr`) are not redirected to a terminal other than the current session's controlling terminal.
Avoid running `source -- /path/to/ble.sh` from within a shell function.
The detailed conditions that require this "more reliable configuration" are explained in [Answer to Discussion #254](https://github.com/akinomyoga/ble.sh/discussions/254#discussioncomment-4284757).

## 1.4 Initialization script `~/.blerc`

User settings are written in the initialization script `~/.blerc` (or `${XDG_CONFIG_HOME:-$HOME/.config}/blesh/init.sh` if `~/.blerc` is not found).
The initialization script is a Bash script that is automatically loaded when `ble.sh` is loaded, so you can use commands that can be used in Bash in the initialization script.
If you want to change the location of the initialization script, specify `--rcfile INITFILE` when `source ble.sh`. For example:
You can use the file [`blerc.template`](https://github.com/akinomyoga/ble.sh/blob/master/blerc.template) in the repository as a template.
(Note that you need to use the commit template file that corresponds to your `ble.sh`).

```bash
# in bashrc

# Example 1: ~/.blerc will be used by default
[[ $- == *i* ]] && source -- /path/to/blesh/ble.sh --attach=none

# Example 2: /path/to/your/blerc will be used
[[ $- == *i* ]] && source -- /path/to/blesh/ble.sh --attach=none --rcfile /path/to/your/blerc
```

## 1.5 Update

Requires Git (`git'), GNU awk (`gawk`), and GNU make (`make`).
If you are using `ble-0.3` or higher, please run `ble-update` with `ble.sh` loaded.

```bash
$ ble-update
```

If you are using `ble-0.4` or higher, you can update with the following command without loading `ble.sh`.

```bash
$ bash /path/to/ble.sh --update
```

Otherwise, you can get and install the latest version with `git pull` as follows.

```bash
cd ble.sh   #*Enter the git repository you already have
git pull
git submodule update --recursive --remote
make
make INSDIR="$HOME/.local/share/blesh" install
```

## 1.6 Uninstall

Basically, there is no problem if you simply delete the `ble.sh` directory and the settings added by the user.

- Terminate all `ble.sh` sessions (interactive Bash sessions that are loading `ble.sh`).
- Delete relevant user data. If you want to keep this data, please skip it if necessary.
  - Delete any lines you added to `.bashrc`.
  - Delete the `blerc` configuration file (`~/.blerc` or `~/.config/blesh/init.sh`) if it exists.

## 2.2 Disabling each function

One of the frequently asked questions is how to disable each feature.
The method for disabling each function is summarized below.
Settings that bring the behavior of `ble.sh` closer to Readline [`config/readline`](https://github.com/akinomyoga/blesh-contrib/blob/master/config/readline.bash)
(You can also read it with `ble-import config/readline`).

```bash
# Disable syntax coloring
bleopt highlight_syntax=

# Disable syntax coloring based on file name
bleopt highlight_filename=

# Disabling syntax coloring based on variable type
bleopt highlight_variable=

# Disable autocompletion (autocompletion is enabled by default in Bash 4.0 and later)
bleopt complete_auto_complete=
# Tip: Alternatively, you can specify a delay in milliseconds to start autocomplete.
bleopt complete_auto_delay=300

# Disabling autocompletion based on command history
bleopt complete_auto_history=

# Disabling ambiguity completion
bleopt complete_ambiguous=

# Disabling menu completion with TAB
bleopt complete_menu_complete=

# Disable menu auto-filtering (enabled by default in Bash 4.0 and later)
bleopt complete_menu_filter=

# Disabling end-of-line marker "[ble: EOF]"
bleopt prompt_eol_mark=''
# Tip: You can also specify other strings instead.
bleopt prompt_eol_mark='⏎'

# Disable exit status marker "[ble: exit %d]"
bleopt exec_errexit_mark=
# Tip: You can also specify other strings instead.
bleopt exec_errexit_mark=$'\e[91m[error %d]\e[m'

# Disable command execution time marker "[ble: elapsed 1.203s (CPU 0.4%)]"
bleopt exec_elapsed_mark=
# Tip: You can also specify another string instead.
bleopt exec_elapsed_mark=$'\e[94m[%ss (%s %%)]\e[m'
# Tip: You can also change the conditions for displaying markers.
bleopt exec_elapsed_enabled='sys+usr>=10*60*1000' #Example: Displayed when total CPU time is 10 minutes or more

# Disable exit marker "[ble: exit]"
bleopt exec_exit_mark=

# Disabling other markers "[ble: ...]"
bleopt edit_marker=
bleopt edit_marker_error=
```

## 2.3 Ambiguous character width

The setting `char_width_mode` can be used to control the width of characters with ambiguous width (characters whose Unicode reference characteristic `East_Asian_Width` is `A` (Ambiguous)).
There are currently four choices: `emacs`, `west`, `east`, and `auto`.
If the setting value `emacs` is specified, the default character width in GNU Emacs will be used.
If the setting value `west` is specified, all ambiguous character widths are interpreted as 1 (half-width).
If the setting value `east` is specified, all ambiguous character widths are interpreted as 2 (full-width).
If you specify the setting value `auto`, it will automatically determine whether it is `west` or `east` based on the interaction with the terminal.
The default value is `auto`. This setting item must be set appropriately depending on the behavior of the terminal being used.
For example, to set it to `west` you would do:

```bash
bleopt char_width_mode='west'
```

## 2.4 Character code

The setting `input_encoding` is used to control the character encoding of the input. Currently only `UTF-8` and `C` are supported.
If the setting value `C` is specified, the received byte value is directly interpreted as a character code.
The default value is `UTF-8`. To change the setting to `C`, do the following:

```bash
bleopt input_encoding='C'
```

## 2.5 bells

The setting `edit_bell` is a colon-separated list that controls the behavior of the editing function `bell`.
The values ​​`abell`, `vbell`, and `visual` enable the corresponding bell presentation method.
The value `abell` corresponds to an audible notification and prints the control character <kbd>BEL</kbd> (0x07) to `stderr`.
The value `vbell` corresponds to a screen notification and displays a message on the terminal screen.
The value `visual` corresponds to screen inversion, which uses <kbd>DECSCNM</kbd> to momentarily invert the terminal screen.
By default, only sound notifications are enabled.

The setting `vbell_default_message` specifies the message string to use in screen notifications. The default value is `' Wuff, -- Wuff!! '`.
The setting `vbell_duration` specifies the length of time to display notifications on the screen. The unit is milliseconds. Default value is `2000`.
The setting `vbell_align` specifies the position of the notification on the screen. `left`, `center`, `right` can be specified.

For example, you can disable sound notifications and set/enable screen notifications using the settings below.

```bash
bleopt edit_bell=vbell vbell_{default_message=' BEL ',duration=3000,align=right}
```

```bash
ble-import -d integration/fzf-key-bindings
```

The option `-d` specified in `ble-import` above reads the specified file.
delay. If configured this way, the specified file will not be prompted for.
It will be loaded in the background after. For more information, see [`ble-import` - Instructions

Please take a look.

### If you have additional settings for fzf

If you want to run additional configuration code after loading the `fzf` configuration, for lazy loading of the fzf configuration above,
If you simply write the configuration code following the above settings, it will not work.
In this case, there are four methods.
The simplest method is to disable lazy loading without specifying the `-d` option [1].

```bash
# [1] Do not use option -d
ble-import integration/fzf-completion
ble-import integration/fzf-key-bindings
<settings>
```

However, using the above method increases initialization time. Alternatively,
Additional configuration using `ble-import -d` [2] or `ble/util/idle.push` [3] is similarly slow.
It can be extended. Or, when the fzf configuration file has finished loading,
Hooks can also be configured using `ble-import -C` [4].

```bash
# [2] Use ble-import -d for additional settings
ble-import -d integration/fzf-completion
ble-import -d integration/fzf-key-bindings
ble-import -d '<filename containing the settings>'

# [3] Register additional settings with ble/util/idle.push
ble-import -d integration/fzf-completion
ble-import -d integration/fzf-key-bindings
ble/util/idle.push '<settings>'

# [4] Register additional settings with ble-import -C
ble-import -d integration/fzf-completion
ble-import -d integration/fzf-key-bindings
ble-import -C '<settings>' integration/fzf-key-bindings
```

# 3 tips

## 3.1 Multiline mode

If the command line contains a newline, you are in multiline mode.

<kbd>C-v C-j</kbd> or <kbd>C-q C-j</kbd> allows you to enter a newline as part of the command line.
In multiline mode, <kbd>RET</kbd> (<kbd>C-m</kbd>) inserts a new line instead of executing a command.
In multiline mode, use <kbd>C-j</kbd> to execute the command.

When `shopt -s cmdhist` is set (the default), if the command line is not syntactically closed when you press <kbd>RET</kbd> (<kbd>C-m</kbd>), it will insert a newline instead of executing the command.

## 3.2 Vim mode

Vim mode is enabled when `.bashrc` is set to `set -o vi` or `.inputrc` is set to `set editing-mode vi`.
For detailed settings of Vim mode, please see [Wiki page](https://github.com/akinomyoga/ble.sh/wiki/Vi-(Vim)-editing-mode).

## 3.3 Auto-completion

Starting with Bash 4.0, auto-completion is enabled and provides predictive suggestions.
Enter <kbd>S-RET</kbd> to confirm the suggestion (or <kbd>right</kbd>, <kbd>C-f</kbd> or <kbd>end</kbd> if you are at the end of the edit string).
To partially confirm only the first word of the displayed candidates, enter <kbd>M-f</kbd> or <kbd>M-right</kbd>.
To confirm with the current candidate and execute the command as is, enter <kbd>C-RET</kbd> (*if your terminal supports it).
If your device does not support it, please refer to [Manual §3.6.4](https://github.com/akinomyoga/ble.sh/wiki/Manual-%C2%A73-Key-Binding#user-content-sec-modifyOtherKeys-manual).


## 3.4 Static abbreviation expansion

By registering a specific word in static abbreviation expansion, you can expand it into any string of characters you like.
Static abbreviation expansion occurs when you type <kbd>SP</kbd> immediately after a word that matches a registered word.
For example, if you configure the following settings, when you press <kbd>SP</kbd> after entering `command L`, the command line will be expanded to `command | less`.

```bash
# blerc
ble-sabbrev L='| less'
```

It is also recommended that you register words starting with `\` in static abbreviation expansion as words that are unlikely to be included in the command you actually want to execute.

```bash
# blerc
ble-sabbrev '\L'='| less'
```

Static abbreviation expansions starting with `~` are also expanded in <kbd>/</kbd>. This can be used to mimic Zsh's named directories.
For example, if you type `~mybin/` under the following configuration, it will expand to `/home/user/bin/`, etc. (if `HOME=/home/user`).

```bash
# blerc

ble-sabbrev "~mybin=$HOME/bin"
```

For other details, please see [Manual's static abbreviation expansion section](https://github.com/akinomyoga/ble.sh/wiki/Manual-%C2%A77-Completion#user-content-sec-sabbrev).
